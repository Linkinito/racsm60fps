Ratchet & Clank: Size Matters
Overcompensated
Format de sauvegarde UCES00420 — état du reverse-engineering et document de passation
Version 0.1 — 16 septembre 2026
OBJECTIF
Permettre à un autre analyste de reprendre le travail sans dépendre du contexte de conversation. Le document sépare les faits observés, les corrélations fortes, les hypothèses et les tâches restant à valider.
PORTÉE
Cette version documente surtout l’organisation physique de DATA0/SECURE.BIN, la correspondance RAM <-> sauvegarde, le système générique de flags, les Skill Points, les blocs RE00 et les zones candidates pour une extension Overcompensated. Elle ne prétend pas encore nommer chaque champ du GameState ni chaque structure auxiliaire.
1. Résumé exécutif
La sauvegarde solo de la version européenne UCES00420 est contenue dans un dossier DATA0 avec trois fichiers : PARAM.SFO, ICON0.PNG et SECURE.BIN. Le gameplay persistant est stocké dans SECURE.BIN sous forme chiffrée PSP Savedata ; une fois déchiffré, son payload fait exactement 0x56F20 octets, soit 356 128 octets.
Le début de ce payload contient une structure de jeu persistante directement corrélable à la RAM, suivie de quatorze blocs fixes de 0x4000 octets commençant par la signature RE00, puis d’une grande région auxiliaire jusqu’à la fin du fichier. Les Skill Points sont six octets de flags situés physiquement à 0x8F7–0x8FC dans le payload clair, mais le code les adresse par indices logiques 0x77–0x7C via une base interne de 0x880.
La limite de 48 bits observée appartient donc au champ vanilla des Skill Points et ne constitue pas une limite générale de la sauvegarde. En revanche, les octets immédiatement postérieurs à 0x8FC contiennent déjà d’autres données : il ne faut pas étendre le champ vanilla en écrivant à la suite sans remapper le GameState.
Une zone de 86 516 octets, 0x3E4EC–0x536DF, est entièrement nulle dans deux états de sauvegarde indépendants actuellement disponibles. Cette plage est une candidate très intéressante pour la persistance Overcompensated, mais elle ne doit pas être considérée comme libre avant validation par analyse des accès mémoire et tests sur davantage de modes de jeu.

5. Chiffrement PSP Savedata et déchiffrement
CONFIRMÉ
SECURE.BIN fait 0x56F30 octets sur disque, alors que son payload clair fait 0x56F20 octets. Le différentiel de 16 octets est cohérent avec l’enveloppe cryptographique utilisée par le Savedata PSP.
Le RAM dump contient une structure sceUtilitySavedata complète pointant vers un buffer clair de la même longueur que le payload déchiffré. L’analyse précédente a également identifié et utilisé avec succès le mode Savedata 5 et la clé de 16 octets 33 33 33 01 02 03 04 05 06 07 08 09 A0 A1 A2 A3 pour reconstruire le plaintext actuel via les routines compatibles PPSSPP/libkirk.
Pour reproduire le déchiffrement, la référence recommandée est l’implémentation PPSSPP elle-même, notamment Core/Dialog/SavedataParam.cpp, Core/HLE/sceChnnlsv.cpp et ext/libkirk. Il est préférable de réutiliser ces routines ou un outil compatible plutôt que d’implémenter un schéma cryptographique approximatif à partir de zéro.

7. GameState persistant : 0x00000–0x01C3F
Cette première zone est le cœur de la progression globale. La correspondance RAM <-> disque est démontrée par plusieurs accès de code et par la valeur des boulons : le jeu accède au même offset relatif 0x1C28 dans le GameState que celui trouvé dans le payload déchiffré.

8. Système générique de flags et Skill Points
CONFIRMÉ
Dans LEVEL_01.PRX, la routine à .text+0x21B14 lit un octet à GameState + 0x880 + byteIndex puis applique 1 << bitIndex. La routine à .text+0x21B38 modifie le bit correspondant après avoir masqué la valeur à 1 bit.
Les valeurs 0x77–0x7C ne sont donc pas des offsets physiques de fichier : ce sont des indices d’octets passés à ce système générique. L’adresse physique dans le GameState est obtenue en ajoutant 0x880, d’où 0x880 + 0x77 = 0x8F7 et 0x880 + 0x7C = 0x8FC.
GetFlag(byteIndex, bitIndex):
    value = *(uint8_t *)(GameState + 0x880 + byteIndex)
    return value & (1 << bitIndex)
SetFlag(byteIndex, value, bitIndex):
    ptr = GameState + 0x880 + byteIndex
    *ptr = (*ptr & ~(1 << bitIndex)) | ((value & 1) << bitIndex)
Pokitaru fournit une validation explicite de l’organisation par bits : son PRX interroge l’indice logique 0x77 avec les bits 0, 1 et 2, tandis que Ryllus interroge le même octet avec les bits 4, 5 et 6. Cette organisation suggère fortement des demi-octets de quatre flags par destination, avec des slots inutilisés lorsque le niveau possède moins de quatre Skill Points.

ATTENTION
Les octets 0x8FD et suivants ne constituent pas une extension implicite du tableau de Skill Points. D’autres flags persistants y sont déjà stockés et des indices logiques comme 0x80 ou 0x82 sont utilisés par le jeu; une écriture naïve au-delà de 0x8FC risquerait de corrompre la progression.
9. Les quatorze slots RE00
À partir de 0x1C40, la sauvegarde réserve quatorze slots de 0x4000 octets, chacun commençant par la signature ASCII RE00. Leur présence et leur espacement sont confirmés, mais leur fonction exacte n’est pas encore attribuée; il faut éviter de les appeler arbitrairement “saves de niveaux” ou “replays” sans preuve supplémentaire.

12. Implications pour Overcompensated
Les 48 bits vanilla sont suffisants pour un prototype rapide, car 25 Skill Points semblent utilisés et plusieurs bits restent disponibles. Ils ne constituent toutefois pas une bonne architecture définitive pour Speed Points, Curiosity Points et Skill Issues : le code vanilla parcourt ces octets dans divers contextes, et mélanger les nouveaux points aux flags originaux pourrait modifier des compteurs, déblocages ou comportements non désirés.
L’architecture recommandée est une structure persistante Overcompensated séparée, stockée dans une zone certifiée inutilisée du payload existant ou, à défaut, dans un fichier annexe géré par le plugin. Une zone interne est préférable si elle peut être prouvée sûre, car le jeu et PPSSPP continueraient alors à gérer normalement le chiffrement et l’écriture de SECURE.BIN.
Proposition de structure, uniquement après validation d’un emplacement libre :
struct OCSaveHeader {
    char     magic[4];      // "OCSV"
    uint16_t version;
    uint16_t size;
    uint32_t flags;
};
// Puis : bitsets Speed / Curiosity / Skill Issues, meilleurs temps, compteurs, etc.
// Prévoir une version de format pour les migrations futures.
13. Ce qu’il ne faut pas considérer comme acquis
Plusieurs points peuvent facilement devenir des “fausses certitudes” si le relais ne connaît que les conclusions sans leur niveau de preuve. Les éléments ci-dessous doivent rester explicitement marqués comme ouverts jusqu’à validation expérimentale ou lecture complète du code concerné.
Ne pas supposer
Pourquoi
“Les 86 516 octets sont libres.”
Ils sont nuls dans deux saves seulement; un autre mode, une progression tardive ou une fonctionnalité rare peut les utiliser.
“RE00 est un replay / un niveau / un cache précis.”
Seuls la signature, le nombre de slots, leur taille et certains champs sont confirmés; la sémantique reste inconnue.
“Les 23 bits Skill Point inutilisés sont sans conséquence.”
Ils appartiennent au champ vanilla et peuvent être lus par des compteurs/déblocages; il faut auditer les consommateurs.
“0x7D est le septième octet Skill Points.”
0x7D est un nouvel indice générique de flags, pas une continuation garantie du système Skill Point.
“Le mapping planète <-> nibble est définitivement prouvé partout.”
Pokitaru/Ryllus sont explicitement vérifiés; le reste suit un mapping de travail cohérent qui mérite une validation PRX systématique.
“La taille du fichier peut être changée sans conséquence.”
Aucun test de compatibilité n’a encore validé une extension physique de SECURE.BIN; privilégier d’abord une zone interne certifiée.

15. Expériences prioritaires à mener
La meilleure méthode pour nommer les champs restants est le diff contrôlé : deux sauvegardes issues du même point de départ où une seule variable connue change. Cette méthode doit être complétée par des breakpoints ou write watches PPSSPP afin de distinguer les champs réellement persistants du padding qui reste nul par hasard.
